# Delivery incident and audit — 6 November 2026

## Findings

- Fresh CRM events and AI generation were working. The deferred queue was not healthy:
  over 2,300 overdue rows, including leases stuck since October.
- Telegram rejected many deferred sends with HTTP 400. The old client retained only
  the status, so the precise Telegram rejection description cannot be recovered
  retrospectively. Do not claim the particular payload defect has been proven.
- Every error was put immediately back into pending, allowing permanent failures
  to starve newer notifications. Cron runs could overlap and claim 50 rows each.
- Callback and deferred delivery ownership checks used the stored card assignment.
- Daily summaries did not apply production location/sales scope consistently.
- npm audit found a moderate fast-uri advisory, corrected with compatible patches.

## Containment requested by the owner

- AUTOMATION_ENABLED=false on Railway. Webhook ingestion stays available.
- Existing pending/processing deferred rows were moved to held, not deleted.
- 246 newly delivered, stale October Telegram messages were identified using the
  delivery journal and submitted to Telegram deleteMessages. All batches succeeded.
- No test Telegram messages or HighLevel writes were performed.

## Repairs

- Single deferred worker; one leased item at a time, bounded work per run.
- Persisted attempt count and sanitized error category, exponential retry delay,
  terminal handling for permanent rejection, and review for uncertain sends.
- Already-delivered card/recipient pairs are checked before another attempt.
- Interrupted leases become uncertain instead of automatically replaying.
- Recheck live CRM owner before delayed delivery and AI rewrites; obsolete drafts
  and expired meetings are not delivered.
- Scope daily summaries and /today to configured locations and sales. Preserve
  admin copies even for a tracked sales user whose Telegram delivery is disabled.
- Catch scheduled task failures, stop schedules on shutdown, and reduce idle queue
  polling to at most one request every five seconds after idle backoff.
- Migration 005 adds only attempts and last_error; validated on an isolated Neon
  branch with automatic expiration. No production tables or business records removed.

## Safe resumption

Do not automatically re-enable automation as part of this incident. On an explicit
owner request to resume, set DEFERRED_DELIVERY_RESUME_AT to the new UTC cutover,
then enable AUTOMATION_ENABLED. On startup, pending/retry/processing records older
than that cutover move to held. Previously held rows stay held.

Keep all existing production location, sales, recipient allowlists and admin IDs.
Never bulk replay the held queue or restore the deleted stale Telegram messages.
Appointment flow still needs a real end-to-end event: no appointment webhook was
observed in this audit. Tests use mocks; they do not prove Telegram delivery.
